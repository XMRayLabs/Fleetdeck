# Security Policy

## Reporting a vulnerability

Do not open a public issue for suspected vulnerabilities. Use the repository owner's GitHub Security Advisory “Report a vulnerability” form. If private reporting has not been enabled yet, contact the maintainer privately and share only the minimum reproduction needed.

Include the affected version, impact, reproduction steps, and any suggested mitigation. Do not include real credentials, private keys, database backups, or secret files.

## Supported version

Security fixes target the latest release on the default branch. Operators should keep Docker base images and npm dependencies current and run `npm run audit:prod` before deployment.

## AI assistance boundary

- AI is optional and disabled until a user saves their own API configuration. Chat Completions-compatible endpoints support HTTP and HTTPS, custom ports, and private/loopback addresses without an allowlist. Authenticated users configuring AI can reach backend-accessible network services; deploy only for trusted operators and restrict egress at the network layer as needed. HTTP transmits API keys and content in plaintext; use it only on trusted networks. DNS is pinned; redirects and HTTPS certificate verification bypasses remain disallowed.
- API keys are encrypted with the deployment encryption key, never returned by the config API, and cleared from the input after saving. Preserve the deployment encryption key securely; database encryption does not defend against a compromised application host.
- Explicit task/log text, bounded conversation history and selected device identities are included in previews. The full device/alias inventory and Nezha telemetry are opt-in. All are untrusted data, not instructions. Passwords used for SSH are not model inputs. Redaction runs on the backend before a separate send confirmation. Heuristics and known-secret matching cannot guarantee removal of unknown, encoded, split or business-specific secrets. Human preview and the chosen provider's data retention policy remain important.
- Model discovery sends only the provider credential to the configured `/models` endpoint, never terminal text. It shares the chat transport's HTTP/HTTPS support, pinned DNS, no-redirect policy and bounded response/time limits. Changing provider addresses requires supplying that provider's key again. Model names are untrusted text. Automatic selection uses name heuristics, not a guarantee of capability or price; it does not automatically retry other models or execute commands.
- Logs/model output are untrusted text, never HTML. The backend validates actions against immutable, owner-bound SSH target scope. Discussion mode cannot execute. Manual mode requires single-use approval of server-held commands and IDs every round. Autonomous mode requires a separate explicit task authorization, then can execute later rounds without individual confirmation within the original scope. This is consequential administrative access, not a command sandbox or a reliable harmful-command detector; root credentials still grant root effects.
- Agent tasks are redacted, encrypted and owner-scoped for listing, detail, export, continuation and deletion. They persist across navigation and reload; drafts do not. Outputs are read from actual owner-scoped orchestration jobs and redacted before persistence, including temporary credential values. Temporary SSH credentials remain memory-only for one round and are never sent to the provider; prompt-based targets require approval again the next round, even in autonomous mode. Non-AI jobs keep their previous output policy. Legacy conversations remain readable as context.
- Tasks are limited to 50 selected hosts, 8 commands per round, 1–20 concurrent hosts per group, 10–1800 second group timeouts, 1–30 rounds and one hour of authorization. At most 5 unfinished and 100 total tasks per user are retained. Connection/key/proxy or API endpoint/key changes invalidate further execution. A backend restart marks thinking/executing tasks interrupted rather than resuming them; approvals are revalidated on use. Legacy preview approvals remain short-lived and are not upgraded into autonomous permission.
- Model/reasoning parameters are selected per task. Provider-default reasoning omits the parameter; explicit choices use reasoning_effort and may fail on incompatible models. No automatic model fallback occurs. The new task runner waits for complete JSON responses before accepting actions, with bounded response/context size, independent per-target output clipping, a three-minute model timeout and cancellation. Hidden reasoning is not displayed.
- Public Nezha monitoring uses pinned, validated public DNS over WSS/443 without credentials or redirects, with bounded messages and timeouts. Arbitrary notes are discarded. Explicit owner-scoped node/device mappings are cleared on URL changes; names/aliases never authorize command execution. Last-active and snapshot timestamps must be considered when diagnosing stale telemetry.
- Subsequent messages and result reviews use the task's initial provider/context consent. Autonomous command loops occur only after explicit task authorization. Pause waits for the current command group; stop requests cancellation and blocks subsequent groups. Neither can roll back completed changes or guarantee termination of detached remote processes. SSH execution channels do not inherit interactive shell state. SSH job cancellation and task deletion are distinct; deleting a task does not erase separate execution records.

## Deployment assumptions

FleetDeck is an administrative system. Deploy it behind HTTPS, restrict network access where possible, enable Passkey or TOTP, and never expose backend, remote-gateway, or guacd ports directly.
